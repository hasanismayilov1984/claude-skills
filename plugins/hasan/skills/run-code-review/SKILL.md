# Run code review

## 1. Find what to review

- Default: the current branch compared with the default branch — `git fetch origin` then `git diff origin/<default-branch>...HEAD`. Find the default branch with `git remote show origin | grep HEAD`.
- If the user names files, a commit, or a PR number, review that instead.
- If there is nothing to diff (e.g. on main with no changes), ask what to review.

Read the changed files fully, not just the diff lines, so you understand the context.

## 2. Check, in this order

1. **Correctness** — wrong logic, unhandled nulls/empty results, off-by-one dates, wrong joins or filters, broken error handling.
2. **Security** — secrets in code, personal data in logs or committed files, SQL injection, unvalidated input passed to `eval`/`exec`/`query`, overly open CORS or permissions.
3. **SQL / data** — join fan-out (duplicated rows), missing `WHERE` on updates/deletes, `SELECT *` in production code, non-sargable filters, timezone and date-boundary bugs, NULL handling in aggregates.
4. **LLM / GenAI** — numbers generated by the model instead of computed; tool/function schemas that don't match the code; prompts that leak private data; no handling for API errors, timeouts, or rate limits.
5. **Power BI / DAX** (if `.pbip`, `.tmdl`, `.bim`, or DAX files changed) — filter context mistakes, `CALCULATE` misuse, bidirectional relationships, missing date table marking, heavy iterators over large tables.
6. **Maintainability** — duplicated code, dead code, unclear names. Only flag if it matters.

## 3. Report

Rank findings most severe first. For each:

- **file:line**
- **What's wrong** (one sentence)
- **Failure scenario** — concrete input/state → wrong output or crash
- **Fix** — short, specific

End with a one-line verdict: ready to merge / merge after fixes / needs rework.

Skip style nitpicks unless asked. Do not change code unless the user asks.
